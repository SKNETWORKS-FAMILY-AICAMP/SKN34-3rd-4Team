# 03. Golden Set · 검증 데이터

## 1. 왜 Golden Set이 필요한가

공고 수집량이 많더라도 전체 데이터를 매번 사람이 검수할 수는 없습니다.

따라서 팀 전체가 같은 사례를 기준으로 개발·회귀·데모를 수행할 수 있도록 **고정된 검증 데이터 묶음**을 만들었습니다.

Golden Set의 목적:

- DB/Data, Backend, AI Core, Frontend가 같은 공고를 바라보게 함
- Requirement / Evidence / Judgment의 기대값을 고정해 회귀 확인
- 변경공고 전후를 반복 재현
- 특정 회사 한 개에 과적합되지 않도록 복수 합성 회사 Profile 사용
- 발표 Demo와 자동평가를 가능한 한 같은 데이터 계보로 연결

---

## 2. 구성

| 항목 | 규모 |
| --- | ---: |
| 기준 공고 | 20건 |
| Canonical Requirement | 138행 |
| 합성 회사 Profile | 32개 |
| 판정 Case | 40개 |
| 변경 비교 | 8개 |
| Copilot 문맥 평가용 prior-turn input | 8개 |

> 일부 기대값은 프로젝트 개발자가 작성·검토한 DRAFT label입니다. 독립된 제3자 정답집과 동일하게 취급하지 않습니다.

---

## 3. 선정 기준

초기 Core4는 공고 Version, 첨부문서, Requirement 연결 상태가 양호한 변경공고를 우선 선정해 전체 파이프라인을 확인하는 데 사용했습니다.

이후 평가 범위를 20개 공고까지 확장했습니다.

선정 시 확인한 기준:

- 공고번호 / 차수 / 첨부문서 연결
- 실제 원문 확인 가능 여부
- Requirement가 비교적 명확한지
- 변경공고 존재 여부
- 단순 메타데이터 수정이 아니라 Qualification 검증에 의미가 있는지
- Profile 차이로 SATISFIED / UNSATISFIED / UNKNOWN을 재현할 수 있는지

---

## 4. Current Rule Golden Regression

Golden Regression은 **Canonical Requirement를 판정기에 직접 입력**합니다.

현재 Golden Set v0.2 기준:

```text
case                  40
requirement row       138

초안 기대값 일치      110 / 138
SAFE_ABSTENTION       28 / 138
잘못된 확정 판정      0
```

CI gate의 핵심 기준:

```text
dangerous determinate error = 0
exact match >= baseline 110
```

### 무엇을 의미하는가

> 구조화 Requirement가 주어졌을 때 Rule Engine이 기존의 안전한 동작에서 회귀하지 않는가?

### 무엇을 의미하지 않는가

- LLM Requirement Extraction 정확도
- Copilot 답변 정확도
- RAG 전체 정확도
- 실제 사용자 성공률

## 5. Historical 평가와 Current Gate 구분

Copilot v2 평가 당시에는 이전 Rule snapshot에서:

```text
104 / 138 exact
34 / 138 safe abstention
```

이 기록돼 있습니다.

이후 지역 위계 처리, Rule v0.3, Golden fixture/판정 회귀 보강이 반영되면서 **최종 제출 문서의 Current Rule 기준은 110 / 28 / 0**을 사용합니다.

과거 수치는 개선 과정을 설명하는 Historical Evidence로만 사용합니다.

## 6. Demo 데이터

최종 Demo는 **전북대학교 남원글로컬캠퍼스 관련 사례**를 중심으로 구성했습니다.

Copilot Guided Job 실제 모델 격리 평가에서는 합성 Profile J13~J16을 사용했습니다.

- Profile 4개
- 각 Profile × 6 Guided Question
- 총 24턴
- 23/24 COMPLETE
- 1건 PARTIAL

이 결과는 사람 사용자 24명의 성공률이 아니라 **합성 Profile 기반 Actual Model Task 실행 결과**입니다.

---

## 7. 변경공고 검수에서 발견한 실제 문제

Golden 공고를 나라장터 원문과 직접 대조하는 과정에서 팀 DB에 없는 후속 차수를 발견했습니다.

대표적으로 `R26BK01634263`은 기존 DB가 003까지만 보유한 상태에서 실제 나라장터에는 004·005가 존재했습니다.

Backfill 개선 후:

```text
000 ~ 005
```

전체 이력을 저장하고 최종 취소공고까지 확인했습니다.

이 경험 때문에 Golden Set 검증 기준을 다음처럼 강화했습니다.

```text
DB Version
↔ 나라장터 실제 차수
↔ 첨부문서
↔ Requirement
↔ Evidence
↔ Judgment
```

---

## 8. 평가 원칙

- 같은 평가셋으로 Before / After 비교
- 실패 케이스를 제거해 점수를 올리지 않음
- 실패를 보고 수정한 뒤 같은 셋을 재실행한 결과는 독립 holdout이라고 부르지 않음
- Rule / Routing / Retrieval / Citation / Task Completion의 분모를 섞지 않음
- 실제 사용자 평가가 없으면 사용자 성공률을 만들지 않음
- Current 지표와 Historical Snapshot을 구분
