# 03. Golden Set · 검증 데이터

## 1. 왜 Golden Set이 필요한가

공고 수집량이 많더라도 전체 데이터를 매번 사람이 검수할 수는 없습니다.

따라서 팀 전체가 같은 사례를 기준으로 개발·회귀·데모를 수행할 수 있도록 **고정된 검증 데이터 묶음**을 만들었습니다.

Golden Set의 목적은 다음과 같습니다.

- DB/Data, Backend, AI Core, Frontend가 같은 공고를 바라보게 함
- Requirement / Evidence / Judgment의 기대값을 고정해 회귀 확인
- 변경공고 전후를 반복 재현
- 특정 회사 한 개에만 맞춘 판정 로직을 피하기 위해 복수 합성 회사 Profile 사용
- 발표 Demo와 자동평가를 가능한 한 같은 데이터 계보로 연결

## 2. 구성

현재 평가 문서에서 사용하는 대표 구성:

| 항목 | 규모 |
| --- | ---: |
| 기준 공고 | 20건 |
| Canonical Requirement | 138행 |
| 회사 Profile | 합성 Profile 32개 |
| 판정 Case | 40개 |
| 변경 비교 | 8개 |
| Copilot 문맥 평가용 prior-turn input | 8개 |

> Golden 데이터의 일부 기대값은 프로젝트 개발자가 작성한 DRAFT label입니다. 독립된 제3자 정답집과 동일하게 취급하지 않습니다.

## 3. 대표 Core 사례

초기 Core4는 공고 Version, 첨부문서, Requirement 연결 상태가 양호한 변경공고를 우선 선정해 파이프라인 연결을 확인하는 데 사용했습니다.

이후 전체 평가용으로 20건까지 범위를 확장했습니다.

Golden Set 선정 시 확인한 기준:

- 공고번호 / 차수 / 첨부문서 연결
- 실제 원문 확인 가능 여부
- Requirement가 비교적 명확한지
- 변경공고 존재 여부
- 단순 메타데이터 수정이 아니라 Qualification 검증에 의미가 있는지
- 회사 Profile을 바꿔 SATISFIED / UNSATISFIED / UNKNOWN 상태를 재현할 수 있는지

## 4. Rule Regression과 Extraction 평가는 다르다

Golden 회귀에서 사용하는 Canonical Requirement는 판정기를 검증하기 위한 고정 입력입니다.

따라서 다음 수치는 **LLM Extraction 정확도가 아닙니다.**

```text
초안 기대값 일치 110 / 138
안전 보류 28 / 138
잘못된 확정 판정 0건
공고 단위 상태 일치 37 / 40
```

이 수치는 “구조화 Requirement가 주어졌을 때 Rule이 기대 방향으로 판단하는가?”를 보는 회귀 지표입니다.

Requirement Extraction 자체는 별도의 실제 문서 Golden 평가가 필요합니다.

## 5. Demo 데이터

최종 Demo는 **전북대학교 남원글로컬캠퍼스 관련 사례**를 중심으로 구성했습니다.

Copilot Guided Job 실제 모델 격리 평가에서는 합성 Profile J13~J16을 사용했습니다.

- Profile 4개
- 각 Profile × 6 Guided Question
- 총 24턴
- 23/24 COMPLETE
- 1건 PARTIAL

이 결과는 사람 사용자 24명의 성공률이 아니라 **합성 Profile 기반 실제 모델 Task 실행 결과**입니다.

## 6. 변경공고 검수에서 얻은 교훈

수집된 DB만 믿지 않고 나라장터 원문과 공고 차수를 직접 대조하면서 일부 후속 차수가 팀 DB에 빠진 사례도 발견했습니다.

이 경험 때문에 Golden Set을 단순 샘플 데이터가 아니라 다음 검증의 기준으로 사용했습니다.

```text
DB Version
↔ 나라장터 실제 차수
↔ 첨부문서
↔ Requirement
↔ Evidence
↔ Judgment
```

## 7. 평가 원칙

- 동일 평가셋으로 Before / After 비교
- 실패 케이스를 제거해 점수를 올리지 않음
- 실패를 보고 수정한 뒤 같은 셋을 다시 통과한 결과는 “독립 holdout”이라고 부르지 않음
- Rule / Routing / Retrieval / Citation / Task Completion의 분모를 서로 섞지 않음
- 실제 사용자 평가가 없으면 사용자 성공률을 만들지 않음
