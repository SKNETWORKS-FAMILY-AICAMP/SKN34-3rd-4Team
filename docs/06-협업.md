# 06. 협업 방식

## 1. 협업 목표

프로젝트에서는 도구 자체보다 **어떤 정보가 어디에서 관리되는지**를 구분하는 데 집중했습니다.

```text
기획 / 설계 배경
→ Notion

실시간 논의 / 작업현황 / Blocker
→ Discord

코드 / Branch / PR / Review
→ GitHub

핵심 Issue 상태 / 우선순위
→ GitHub Projects

UI 기준
→ Figma

대화·상태 재확인 비용 절감
→ MCP / AI Tools
```

---

## 2. GitHub 중심 개발 흐름

![Collaboration Workflow](./assets/collaboration-workflow.png)

```text
Requirement / Issue
→ Feature / Fix Branch
→ Pull Request
→ Review / Test
→ develop Merge
→ 통합 상태 확인
```

### Branch

- `develop`: 팀 통합 기준
- 기능·수정·문서: 별도 Branch
- PR Review 후 develop 반영
- develop → main: 최종 통합 판단으로 별도 관리

### Pull Request

PR에서는 코드 스타일보다 다음 영향 범위를 함께 확인했습니다.

- 기존 기능 영향
- API / DB / AI Contract
- 테스트 결과
- 다른 파트 후속 작업
- Known Limitation
- 문서 갱신 필요 여부

즉 **PR을 코드 합치기 수단이 아니라 파트 간 계약 확인 지점**으로 사용했습니다.

---

## 3. Discord

Discord는 실시간 대화와 현재 작업 상태 공유에 사용했습니다.

작업현황 공유 템플릿:

```text
오늘 완료
현재 진행 중
오늘 종료 전 예정
Blocker
다른 파트 요청 / 공유사항
관련 링크
```

세부 논의는 가능하면 해당 작업현황 메시지의 Thread에서 이어가도록 했습니다.

### Discord MCP 활용

대화량이 많아질수록 과거 메시지를 다시 읽는 비용이 커졌습니다.

Discord Bridge를 이용해:

- 팀원별 진행상황
- Blocker
- 파트 간 요청사항
- Merge Request / 최근 논의

를 요약해 확인했습니다.

중요한 원칙:

> MCP 요약은 Source of Truth가 아니라 **원문과 PR을 다시 확인하기 위한 탐색 보조 도구**입니다.

---

## 4. Notion

Notion은 다음 용도로 사용했습니다.

- 프로젝트 가이드
- 기획 배경
- 초기 설계
- Golden Set 검토
- 회의 / Decision
- CHANGELOG / 작업 근거 정리

역할을 다음처럼 구분했습니다.

```text
Notion
= 왜 이렇게 설계했는가 / 논의 과정

GitHub docs
= 현재 구현이 실제로 어떻게 동작하는가

Code / Test
= 최종 Source of Truth
```

개발 속도가 빨라 문서와 코드가 어긋날 수 있기 때문에 최종 단계에서는 GitHub 코드·테스트를 기준으로 Current 문서를 다시 검산했습니다.

---

## 5. GitHub Projects

초기 계획 단계에서는 Jira 기반 흐름도 검토했습니다.

개발이 GitHub 중심으로 통합되면서 최종적으로:

```text
Issue
→ Branch
→ PR
→ Review / Test
→ Merge
```

를 핵심 개발 흐름으로 사용했고, GitHub Projects는 주요 Issue의:

- Status
- Priority
- Iteration
- Owner

를 연결해 확인하는 **보조 관리 계층**으로 사용했습니다.

프로젝트 전체의 모든 세부 작업을 Projects 하나에 완전히 종속시키기보다 실제 코드 변경과 PR 기록을 중심으로 추적했습니다.

---

## 6. Figma

Figma는 화면 IA와 UI/UX 개선 기준 공유에 사용했습니다.

대표적으로 확인한 문제:

- 긴 세로 스크롤
- 정보 중요도 구분 부족
- 버튼의 실제 연결성
- 공공기관 시스템처럼 경직된 인상
- Loading / Error / Empty 상태
- 실제 입찰 업무 흐름과 화면 정보 밀도

Frontend 변경은 기능 동작뿐 아니라 사용자가 “무엇을 먼저 봐야 하는지”를 함께 검토했습니다.

---

## 7. AI 도구 사용 원칙

팀은 코드·문서·리뷰 과정에서 AI 도구를 적극 사용했습니다.

하지만 결과를 그대로 merge하는 대신 다음 흐름을 유지하려고 했습니다.

```text
AI 제안
→ 코드 / 문서 확인
→ Test
→ PR Review
→ Merge
```

AI 활용량이 늘수록 설명 가능성을 유지하기 위해 다음 산출물을 보강했습니다.

- CHANGELOG / Current docs
- PR 설명과 영향 범위
- Evaluation fixture
- 테스트 재현 명령
- Current / Historical 문서 상태 구분

목표는 “AI가 작성했다”가 아니라:

> **팀이 AI가 만든 결과를 검증하고, 왜 이렇게 구현했는지 설명할 수 있는 상태**

를 만드는 것이었습니다.

## 8. 정보 흐름 요약

| 도구 | 주요 역할 | 최종 기준 |
| --- | --- | --- |
| Discord | 실시간 논의·Blocker | 원문 대화 |
| Discord MCP | 진행상황 재탐색·요약 | 원문/PR 재확인 |
| Notion | 기획·Decision·설계 배경 | Historical / Planning |
| GitHub | 코드·PR·Review·Test | Current 구현 |
| GitHub Projects | 주요 Issue 상태·우선순위 | 보조 진행 관리 |
| Figma | 화면 IA·UX 기준 | UI 설계 |
| GitHub docs | 현재 구조·평가 정리 | 제출 직전 Current |
| README | 최종 요약 | docs 링크 중심 |

---

## 9. 협업 과정에서 개선한 점

프로젝트 후반부에는 협업 정보를 한 도구에 몰기보다 다음 순서로 정리했습니다.

```text
Code / Test
→ Current docs
→ 제출용 docs
→ README
```

이를 통해 초기 설계안이나 과거 상태가 현재 구현처럼 보이는 문제를 줄이고, 최종 평가자가 실제 구현과 근거를 따라갈 수 있도록 했습니다.
