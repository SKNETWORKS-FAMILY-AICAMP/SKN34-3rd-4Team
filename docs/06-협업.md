# 06. 협업 방식

## 1. 협업 목표

프로젝트에서는 도구를 많이 사용하는 것보다 **어떤 정보가 어디에서 관리되는지**를 구분하는 데 집중했습니다.

```text
기획 / 설계 문서
→ Notion

실시간 논의 / 작업현황 / Blocker
→ Discord

코드 / Branch / PR / Review
→ GitHub

작업 상태 / 우선순위
→ GitHub Projects

UI 기준
→ Figma

반복 조회·요약 보조
→ MCP / AI Tools
```

## 2. GitHub 중심 개발 흐름

![Collaboration Workflow](./assets/collaboration-workflow.png)

```text
Requirement / Issue
→ Feature / Fix Branch
→ Pull Request
→ Review / Test
→ develop Merge
→ 통합 상태 확인
```

### Branch

- `develop`: 통합 기준
- 기능·수정 작업: 별도 Branch
- 개인 기능 PR은 영향 범위를 Review한 뒤 develop에 반영
- develop → main은 최종 통합 판단으로 별도 관리

### Pull Request

PR에서 단순 코드 스타일보다 다음을 확인했습니다.

- 기존 기능 영향
- API / DB / AI Contract 영향
- 테스트 결과
- 다른 파트가 이어서 해야 하는 작업
- Known limitation
- 필요 문서 갱신

---

## 3. Discord

Discord는 단순 채팅이 아니라 **현재 상태 공유 채널**로 사용했습니다.

작업현황 공유 템플릿:

```text
오늘 완료
현재 진행 중
오늘 종료 전 예정
Blocker
다른 파트 요청 / 공유사항
관련 링크
```

세부 논의는 해당 메시지의 Thread에서 이어가도록 했습니다.

### Discord MCP 활용

대화량이 많아 직접 모든 메시지를 다시 읽기 어려운 경우 Discord Bridge를 통해:

- 팀원별 진행상황
- Blocker
- 파트 간 요청사항
- 최근 merge/request 논의

를 요약해 확인하는 보조 흐름을 사용했습니다.

MCP 요약은 작업 상태의 Source of Truth가 아니라 **확인 비용을 줄이는 도구**로 사용했습니다.

---

## 4. Notion

Notion은 다음 역할에 사용했습니다.

- 프로젝트 가이드
- 기획 배경
- 설계안
- Golden Set 검토
- 회의/Decision 기록
- 개인 CHANGELOG와 학습 기록

실제 Current 구현 상태는 Notion 문구를 그대로 사용하지 않고 GitHub 코드·테스트와 대조했습니다.

```text
Notion
= 왜 이렇게 설계했는가 / 논의 과정

GitHub docs
= 현재 구현이 실제로 어떻게 동작하는가
```

---

## 5. GitHub Projects

프로젝트 후반부에는 GitHub Projects를 Issue와 연결해:

- Status
- Priority
- Iteration
- 작업 Owner

를 한 화면에서 확인하려고 했습니다.

모든 세부 작업이 완벽하게 Project로 관리된 것은 아니지만, 최종적으로는 Jira보다 **GitHub Issue → Branch → PR → Review → Merge** 흐름을 중심으로 운영했습니다.

제출 문서에서는 GitHub Projects를 과장해 “전체 업무 자동 관리 시스템”처럼 표현하지 않고 **작업 상태와 우선순위를 연결한 보조 관리 도구**로 설명합니다.

---

## 6. Figma

Figma는 Frontend 화면 구조와 UI/UX 방향 공유에 사용했습니다.

특히:

- 긴 세로 스크롤
- 정보 우선순위
- 공공기관 시스템 같은 경직된 인상
- 버튼 연결성
- Loading / Error / Empty 상태

같은 사용성 문제를 팀에서 공유하고 개선 기준을 맞추는 데 사용했습니다.

---

## 7. AI 도구 사용 원칙

프로젝트에서 AI 도구를 적극 활용했지만, AI가 만든 결과를 그대로 merge하지 않는 것을 원칙으로 했습니다.

```text
AI 제안
→ 코드 / 문서 확인
→ Test
→ PR Review
→ Merge
```

AI를 많이 사용한 만큼 다음을 보완했습니다.

- CHANGELOG / docs
- PR 설명
- 평가 fixture
- 테스트 재현 명령
- Current / Historical 문서 상태 구분

목표는 “AI가 코드를 작성했다”가 아니라 **팀이 결과를 검증하고 설명할 수 있는 상태로 만드는 것**이었습니다.

---

## 8. 협업에서 배운 점

### 장점

- 파트별 병렬 개발 속도 확보
- PR 기반 영향 범위 확인
- Discord로 빠른 Blocker 공유
- MCP로 대화 재확인 비용 감소
- Notion / GitHub 역할 분리

### 개선할 점

- 초기에는 Jira와 GitHub Projects가 혼재
- 작업량이 늘며 과거 결정 추적 비용 증가
- AI 작업 누적 후 “보면 이해되지만 설명하기 어려운” 문제가 발생
- 문서와 코드의 Current 상태가 어긋나는 경우 발생

이를 보완하기 위해 최종 단계에서는:

> **Code/Test → Current docs → 제출 README**

순서로 다시 정리했습니다.
