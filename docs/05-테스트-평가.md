# 05. 테스트 · 평가

## 1. 평가 전략

BidCheck는 하나의 “AI 정확도”로 품질을 설명하지 않습니다.

다음은 서로 다른 실패 원인을 가진 평가입니다.

```text
Data / Collection
→ Requirement Extraction / Evidence
→ deterministic Rule
→ Changed Notice / Revalidation
→ Copilot Routing
→ Document Retrieval
→ Grounded Answer / Citation
→ Multi-turn / Safety
→ Actual Model Task
→ Human User Test
```

따라서 각 지표의 분모와 의미를 분리합니다.

---

## 2. Rule Regression

Golden Set의 Canonical Requirement를 Rule에 직접 입력해 판정 로직을 회귀 검증했습니다.

| 지표 | 결과 |
| --- | ---: |
| Canonical Requirement | 138 |
| 초안 기대값 일치 | 110 / 138 |
| 안전 보류 | 28 / 138 |
| 잘못된 확정 판정 | **0** |
| 공고 단위 상태 일치 | 37 / 40 |

### 해석

이 수치는 Requirement Extraction 정확도가 아닙니다.

> **구조화된 Requirement가 주어졌을 때 Rule이 기대 방향으로 판단하는지**를 보는 고정 회귀입니다.

## 3. Copilot v1 · Product Contract Regression

고정 평가셋:

- Single-turn 80
- Multi-turn 20
- 총 100

최초 유효 실행:

```text
99 / 100
```

1건의 실패는 “저장된 회사정보”를 Profile read가 아니라 Action Request로 오분류한 사례였습니다.

수정 후 같은 고정셋:

```text
100 / 100
```

### 주의

실패를 확인하고 코드를 수정한 뒤 같은 셋을 다시 통과했기 때문에, 수정 후 100/100은 **독립 holdout 성능이 아니라 fixed regression**입니다.

## 4. E0 → E1 → E2 · 자유입력 Routing 개선

### E0 Baseline

사용자가 버튼 문구가 아니라 자기 표현으로 질문했을 때 deterministic router가 정확한 intent에 도달하는지 평가했습니다.

평가셋:

- Document QA 60
- Judgment Explanation 32
- Change Comparison 8
- 총 100

결과:

```text
1 / 100
```

이 낮은 수치를 숨기지 않고 개선 기준선으로 고정했습니다.

### E1

확실한 alias와 실패 UX를 먼저 보완했습니다.

```text
1 / 100
→ 41 / 100
```

### E2

keyword substring의 한계를 해결하기 위해 Semantic Router를 추가했습니다.

단, 모든 요청을 LLM Router에 넘기지 않고:

```text
명확한 UI intent / write
→ deterministic 유지

UNKNOWN / weak read
→ semantic recheck
```

정책을 사용했습니다.

최종 frozen routing set:

```text
100 / 100
```

이 100/100은 **답변 정확도가 아니라 intent routing exact match**입니다.

## 5. E3 · Retrieval 비교

같은 Document QA fixture에서 `k=4` 조건으로 비교했습니다.

| 방식 | Recall@4 | p50 |
| --- | ---: | ---: |
| Dense | 29.17% | 144.50ms |
| Hybrid | **50.00%** | 170.58ms |
| Hybrid + LLM Rerank | 55.56% | 2849.73ms |

### 기술 선택

Rerank가 가장 높은 Recall을 보였지만:

- 추가 모델 호출
- 약 2.8초 p50
- 비용과 운영 복잡도

를 고려해 기본 검색 전략은 **Hybrid**를 선택했습니다.

Current v3.1은 broad/current-section/lexical fallback까지 포함하므로 모든 문서 질문이 항상 Hybrid만 타는 것은 아닙니다.

## 6. Grounded Answer · Prompt v1 → v4

초기 문제:

> Citation이 존재한다고 해서 그 Citation이 질문을 실제로 뒷받침하는 것은 아니다.

개선:

### v1

Citation 존재 여부 중심

### v2

직접 근거가 없으면 abstain

### v3

부분 근거 하나로 전체 조건을 확정하지 않음

### v4

문서의 불완전한 코드·숫자를 모델이 임의 복원하지 않음

최종 구조 지표:

| 지표 | 결과 |
| --- | ---: |
| evaluable | 59 |
| generation | 59 / 59 |
| citation present | 57 / 59 |
| citation version integrity | **100%** |
| strict expected evidence citation | 45.83% |
| total latency p50 | 약 2.93s |
| total latency p95 | 약 5.45s |

`45.83%`는 답변 정답률이 아니라 expected evidence와 citation의 strict matcher입니다.

## 7. v3.1 Claim Validation

자동테스트 통과만으로 생성 문장의 사실성까지 보장되지 않는 문제를 해결하기 위해:

```text
Fact / Source
→ Draft Claim
→ Mechanical Validation
→ Semantic Validation
→ 필요 시 1회 Repair
→ Supported Claim만 게시
```

경계를 추가했습니다.

실제 모델 4-turn 실험에서는:

```text
PARTIAL / PASS / PASS / PARTIAL
```

이 나왔으며, 복합 답변의 coverage와 latency 한계를 그대로 기록했습니다.

## 9. Human User Test

사람 사용자 평가 계획은 다음 과업을 중심으로 설계했습니다.

1. 참가 가능 여부와 이유 찾기
2. 원문 근거 추적
3. 자유 질문
4. 변경공고 영향 확인
5. 확인 필요 정보 반영
6. 외부 AI 처리 범위 이해

평가 항목:

- PASS / PARTIAL / FAIL
- CRITICAL safety
- 완료시간
- 힌트 수
- 잘못된 경로
- 사용자가 이해한 결론
- 신뢰도

### 현재 상태

실제 최종 사람 사용자 결과는 아직 완료 수치로 주장하지 않습니다.

## 11. 핵심 평가 원칙

- 낮은 Baseline도 숨기지 않는다.
- 같은 셋으로 Before / After를 비교한다.
- 실패를 본 뒤 수정한 재평가는 independent holdout이라고 부르지 않는다.
- 더 높은 자동 점수보다 latency·비용·안전성을 포함해 기술을 선택한다.
- 자동테스트와 실제 사용자 평가를 분리한다.
- 서로 다른 분모를 하나의 “챗봇 정확도”로 합치지 않는다.
