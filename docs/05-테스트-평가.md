# 05. 테스트 · 평가

## 1. 평가 전략

BidCheck는 하나의 “AI 정확도”로 품질을 설명하지 않습니다.

서로 다른 실패 원인을 다음처럼 분리했습니다.

```text
Data / Collection
→ Requirement Extraction / Evidence
→ deterministic Rule
→ Changed Notice / Revalidation
→ Copilot Routing
→ Document Retrieval
→ Grounded Answer / Citation
→ Multi-turn / Safety
→ Actual Model Task
→ Human User Test
```

---

이 표의 각 수치는 분모가 다릅니다. 하나의 “챗봇 정확도”로 합산하지 않습니다.

## 3. Current Rule Golden Regression

Golden Set v0.2:

| 지표 | 결과 |
| --- | ---: |
| Case | 40 |
| Canonical Requirement | 138 |
| 초안 기대값 일치 | **110 / 138** |
| SAFE_ABSTENTION | **28 / 138** |
| Dangerous Determinate Error | **0** |

### Gate

```text
잘못된 확정 = 0
exact match >= baseline 110
```

### 해석

이 수치는 Requirement Extraction 정확도가 아닙니다.

Canonical Requirement를 Rule Engine에 직접 넣어:

> **현재 Rule이 안전한 방향에서 회귀하지 않는가**

를 보는 고정 회귀입니다.

## 5. E0 → E1 → E2 · 자유입력 Routing

### 평가셋

- Document QA 60
- Judgment Explanation 32
- Change Comparison 8
- 총 100

### E0 Baseline

```text
1 / 100
```

버튼/키워드 중심 흐름에서는 동작했지만 자연스러운 사용자 표현이 대부분 목표 기능에 도달하지 못했습니다.

### E1

확실한 alias와 실패 UX를 deterministic하게 보완했습니다.

```text
1 / 100
→ 41 / 100
```

### E2

Substring false positive를 해결하기 위해 Semantic Router를 추가했습니다.

정책:

```text
명확한 UI intent / write
→ deterministic 유지

UNKNOWN / weak deterministic read
→ Semantic recheck

Semantic 실패
→ deterministic fallback
```

최종 frozen routing set:

```text
100 / 100
```

이 100/100은 **답변 정확도가 아니라 intent routing exact match**입니다.

## 6. E3 · Retrieval 비교

동일 Document QA fixture에서 `k=4`, `fetch_k=12` 조건으로 비교했습니다.

| 방식 | Recall@4 | Case Any-hit@4 | Case All-hit@4 | p50 |
| --- | ---: | ---: | ---: | ---: |
| Dense | 29.17% | 32.20% | 27.12% | 144.50ms |
| Hybrid | **50.00%** | 52.54% | 49.15% | 170.58ms |
| Hybrid + LLM Rerank | **55.56%** | 57.63% | 57.63% | 2849.73ms |

### 기술 선택

Rerank가 Recall은 더 높았지만:

- 추가 모델 호출
- p50 약 2.85초
- 비용 증가
- 운영 복잡도

를 고려해 기본 검색 전략은 **Hybrid**를 선택했습니다.

Current v3.1은 broad/current-section/lexical fallback까지 포함하므로 모든 문서 질문이 항상 Hybrid만 사용하는 것은 아닙니다.

## 7. Grounded Answer · Prompt v1 → v4

초기 문제:

> Citation이 존재한다고 해서 그 Citation이 질문을 실제로 뒷받침하는 것은 아니다.

개선 과정:

```text
v1 Citation 존재 중심
↓
v2 직접 근거 없으면 abstain
↓
v3 partial evidence를 전체 결론으로 확대 금지
↓
v4 원문 오류를 모델이 임의 복구하지 않음
```

최종 구조 지표:

| 지표 | 결과 |
| --- | ---: |
| evaluable | 59 |
| generation | 59 / 59 |
| citation present | 57 / 59 |
| citation version integrity | **100%** |
| strict expected evidence citation | 45.83% |
| total latency p50 | 약 2.93s |
| total latency p95 | 약 5.45s |

`45.83%`는 답변 정답률이 아니라 **frozen expected excerpt와 citation source의 strict matcher**입니다.

## 8. v3.1 · Claim Validation

자동테스트가 통과해도 생성 산문이 서버 사실과 반대일 수 있는 경계를 추가로 점검했습니다.

```text
Fact / Source
→ Draft Claim
→ Mechanical Validation
→ Semantic Validation
→ 필요 시 1회 Repair
→ Supported Claim만 게시
```

실제 모델 4-turn:

```text
PARTIAL / PASS / PASS / PARTIAL
```

복합 답변의 coverage와 latency 한계를 숨기지 않고 그대로 기록했습니다.

## 10. Human User Test

실사용자 관점 평가 계획:

1. 참가 가능 여부와 이유 찾기
2. 원문 근거 추적
3. 자연어 공고 질문
4. 변경공고 영향 확인

6. 외부 AI 처리 범위 이해

평가 항목:

- PASS / PARTIAL / FAIL
- CRITICAL safety
- 완료시간
- 힌트 수
- 잘못된 경로
- 사용자가 이해한 결론
- 신뢰도

### Current

실제 최종 사람 사용자 결과는 완료된 수치로 주장하지 않습니다.

## 13. 평가 원칙

- 낮은 Baseline도 숨기지 않는다.
- 같은 셋으로 Before / After를 비교한다.
- 실패를 본 뒤 수정한 재평가는 independent holdout이라고 부르지 않는다.
- Retrieval / Routing / Rule / Citation / Task Completion을 하나의 정확도로 합치지 않는다.
- 가장 높은 offline metric보다 latency·비용·운영 안정성까지 포함해 기술을 선택한다.
- 자동평가와 실제 사용자 평가를 구분한다.
- Current와 Historical Snapshot을 구분한다.
