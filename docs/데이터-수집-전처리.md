## 1. 개요

나라장터(G2B) 공개 API를 통해 실제 입찰공고 데이터를 수집하고, 첨부문서 텍스트 추출 → 의미 단위 분할 → LLM 구조화 추출 → 원문 대조 검증까지 이어지는 전처리 파이프라인을 통해 참가자격 판정에 쓸 수 있는 구조화 데이터를 만들었다.

## 2. 데이터 출처 및 라이선스

| 항목 | 내용 |
|---|---|
| 출처 | data.go.kr 나라장터(G2B) 공개 API (공공데이터포털) |
| 접근 방식 | `G2B_SERVICE_KEY` 발급 후 API 호출. 업종/품목/기관 마스터데이터는 별도 공공데이터 코드표를 최초 1회 임포트 |
| 라이선스/이용조건 | 조달청_나라장터 입찰공고정보서비스(data.go.kr) 페이지 기준 "이용허락범위 제한 없음", 무료 제공, 자동승인(개발·운영 단계 모두). 포털 전체 공통 공공누리 등급 표기는 별도로 확인되지 않았으나, 이 API 자체의 이용 제한이 없다는 점은 출처 페이지에서 확인함 ([data.go.kr](https://www.data.go.kr/data/15129394/openapi.do), 2026-09-16 확인) |

> ⚠️ **비공개 원칙 (제안, 미확정)** — API 원본 응답 전체·원문 첨부파일 실물을 저장소에 포함할지 여부는 아직 팀 확정 사항이 아니다. 일반적으로 원본 대용량 데이터는 Git에 커밋하지 않고 대표 샘플·요약 문서만 포함하는 방식을 권장하나, 우리 팀의 실제 제출 방침은 별도 확인 필요

> ⚠️ **민감정보** — 첨부문서(제안서·실적증명서 등) 원문에는 담당자 성명 등 개인식별정보가 포함될 수 있고, 실제로 `company_staff` 등 담당자 성명을 저장하는 테이블이 스키마에 존재한다. 현재 파이프라인은 이런 정보를 별도로 마스킹·제외하지 않고 원문 그대로 추출·저장하는 것으로 보인다(스키마 확인 기준, 2026-09-16). Gate 1 기준(민감정보 확인)에 해당하는 항목으로, 마스킹 여부·범위는 팀 논의가 필요하다

## 3. 수집 범위와 제외 기준

### 3-1. 수집 범위
- 기간 제한 없이 가능한 한 넓게 수집 (과거 공고 + 진행 중인 공고 모두 포함)
- 판정 로직 검증에 필요한 케이스가 고르게 포함되도록 정정·변경공고, 재공고, 위험조항 관련 공고를 우선 확보하는 방향으로 운영
- 중복 방지: 공고번호+차수 기준 UNIQUE 제약으로 이미 수집된 버전은 skip

### 3-2. 제외 기준
> ⚠️ **확인 필요** — business_type(용역/물품/공사/외자/기타) 등 특정 유형을 의도적으로 제외했는지는 이 문서 작성 시점에 팀 내 확정 기록을 찾지 못했다. 수집 담당(백엔드·전진환)에게 2026-09-16 확인 요청했으나 아직 회신 없음. 수집 담당과 교차 확인 후 반영 권장

- 추출 단계에서 제외(실질적으로 판정에 활용되지 못한) 건은 4-1 표 참고 — 형식 미지원(UNSUPPORTED)·추출 실패(FAILED)·빈 문서(EMPTY)로, 사유별 건수를 투명하게 남기고 조용히 누락하지 않는다

## 4. 데이터 전처리

### 4-1. 첨부문서 텍스트 추출 현황
*(2026-09-15 기준, 라이브 프로덕션 DB 직접 쿼리)*

수집된 첨부문서는 `extraction_status`로 추출 성공 여부를 관리하며, 추출된 텍스트는 `extracted_text`·`extracted_blocks`(블록 단위 구조 보존)로 저장한다.

| 추출 상태 | 건수 | 비율 |
|---|---|---|
| EXTRACTED (성공) | 4,529 | 93.8% |
| UNSUPPORTED (미지원 포맷) | 220 | 4.6% |
| FAILED (추출 실패) | 42 | 0.9% |
| EMPTY (빈 문서) | 29 | 0.6% |
| PENDING (대기) | 6 | 0.1% |

### 4-2. 전처리 파이프라인 단계

| 단계 | 이름 | 설명 |
|---|---|---|
| 1 | 원문 수집 | G2B API로 공고·차수·첨부문서 메타데이터 및 원본 파일 확보, `payload_hash`로 원본 보존 |
| 2 | 텍스트 추출 | 첨부문서(PDF/HWP 등)에서 텍스트·블록 구조 추출(`extracted_blocks`), 실패/미지원 포맷은 상태값으로 명시 기록 (4-1 표) |
| 3 | 의미 단위 분할 (Semantic Chunking) | 추출된 블록을 의미 단위로 분할 |
| 4 | 키워드 기반 검색 (Keyword Retrieval) | 분할된 청크에서 요건 후보 구간을 키워드 기준으로 검색·추출 대상 선정 |
| 5 | LLM 구조화 추출 | 후보 구간에서 자격요건(업종/실적/인증/지역 등)을 구조화된 값으로 추출 |
| 6 | 원문 대조 검증 (Grounding Validation) | LLM이 추출한 모든 값을 공고 원문과 직접 대조. 원문에 없는 값은 버리고(`DETAIL_NOT_FOUND_IN_SOURCE`) 원문에서 잘라낸 구간만 저장 |
| 7 | 정규화 및 표준코드 매핑 | 자유서술 표현을 업종코드 등 표준 코드로 매핑 |
| 8 | 요건·근거·판정 산출 | Requirement / Evidence / Judgment 구조로 최종 저장 |

> 이 파이프라인은 임베딩 기반 벡터 검색이 아니라 의미 단위 분할(3단계) + 키워드 기반 검색(4단계) 구조를 사용한다. 별도의 벡터 인덱스·임베딩 저장 테이블은 없다(라이브 DB information_schema 대조로 vector/embedding 계열 테이블 부재 확인, 2026-09-15). 이는 의도된 설계로 판단된다 — 2026-09-10 llm-rag 채널에서 홍규님이 재현님 작업 방향을 정리하며 "벡터/의미 기반 검색은 현재 제품의 기본 검색 경로에 적용하지 않고, 먼저 현재 검색/추출 구조를 실제 골든셋으로 평가한 뒤 검색 성능에 문제가 확인되면 그때 고도화 대상으로 검토한다"고 명시했다. ⚠️ 다만 이는 재현님 본인이 아닌 홍규님을 통해 전달된 내용이며, 이 문서 작성 관련해 재현님께 직접 재확인을 요청했으나(2026-09-16) 아직 회신을 받지 못했다.

### 4-3. 추출 안정성 개선 이력

같은 공고를 반복 분석했을 때 추출 결과(요건 개수·유형)가 흔들리는 비결정성 문제가 있었고, 다음 작업으로 개선을 진행 중이다.

| PR | 상태 | 내용 |
|---|---|---|
| #135 | 2026-09-14, 완료 | 샘플링 고정 실패, 원문 대조 누락, 분류 비결정성 세 갈래 원인 수정. 이후 PR들(#132~#134)이 참조한 골든 회귀 기준(110/28/0)이 이 수정을 반영한 값과 일치해, develop에 반영된 것으로 판단됨 |
| #136 | 2026-09-15, 진행 중 — ⚠️ 이 문서 작성 시점 기준 develop 미병합 | ANY_OF 조건 처리, 이중 분류 병합, 업종코드 원문 기반 보정(`salvaged_from_source`), 잘못된 확정 경로 차단. 2026-09-15 17:19 기준 코드 리뷰는 승인(APPROVE) 방향이나, "최신 develop 반영 + CI 재확인 후 merge"가 조건으로 남아있어 실제 병합은 아직 확정되지 않았다 |

> 참고: 6번 골든셋 결과(110/28/0 등)는 frozen canonical requirements를 판정기에 직접 입력해 측정하는 지표라, 실제 LLM 추출 과정을 거치지 않는다. 따라서 #135·#136 같은 추출 파이프라인 변경과 무관하게 값이 유지된다 — #135 PR에서도 "판정 코드는 안 건드렸고 골든 회귀 110/28/0 그대로"라고 명시함. #136이 실제로 개선하는 것은 이 숫자가 아니라 "같은 공고를 반복 분석해도 같은 결과가 나오는지"(추출 재현성)이며, 이를 검증하는 별도 스크립트(`check_extraction_determinism.py`)가 존재한다.
