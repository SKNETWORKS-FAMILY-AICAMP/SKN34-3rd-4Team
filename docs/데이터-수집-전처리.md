# 수집 데이터 · 전처리 · 공용 DB

작성: 정예린 (DB/Data)  
프로젝트: **나라장터 변경공고 대응형 입찰 제출 검증기 · BidCheck**  
최종 제출 문서 기준: 2026-09-17

---

## 1. 개요

BidCheck는 나라장터(G2B) 공개 API를 통해 실제 입찰공고와 공고 이력을 수집하고, 첨부문서를 추출·구조화하여 참가자격 판정과 변경공고 재검증에 사용할 수 있는 데이터로 변환합니다.

전체 흐름:

```text
G2B 공고 / 변경공고
→ 공고·차수·첨부문서 수집
→ 원문 파일 저장
→ HWP/HWPX/PDF 텍스트 추출
→ extracted_blocks
→ AI Core 후보 문맥 선택
→ LLM 구조화 추출
→ 원문 Grounding Validation
→ Canonical Mapping
→ Requirement / Evidence
→ deterministic Judgment
```

데이터 파트의 핵심 목표는 단순히 공고 건수를 늘리는 것이 아니라 다음 관계를 유지하는 것입니다.

```text
공고번호
↔ 나라장터 차수
↔ 첨부문서
↔ 추출 원문
↔ Requirement
↔ Evidence
↔ Judgment
```

## 2. 데이터 출처

| 항목 | 내용 |
| --- | --- |
| 주요 출처 | data.go.kr 나라장터(G2B) 공개 API |
| 주요 데이터 | 입찰공고, 변경/정정 차수, 첨부문서 메타데이터 및 원문 |
| 기준정보 | 업종·품목·기관 코드표 |
| 인증 | `G2B_SERVICE_KEY` |
| 운영 DB | PostgreSQL / Supabase |
| Schema 관리 | Alembic Migration |

조달청 나라장터 입찰공고정보서비스의 공개 API를 개발 데이터의 기본 출처로 사용했습니다.

대용량 원본 응답과 실제 첨부문서는 제출 저장소에 직접 포함하지 않고, 코드·대표 화면·요약 문서·검증 결과를 제출 산출물로 관리합니다.

> 원문 첨부에는 담당자 정보 등 개인식별정보가 포함될 수 있습니다. 본 프로젝트는 원문 대량 공개가 아니라 서비스 내부 검증을 목적으로 사용하며, 별도의 자동 비식별화 파이프라인은 최종 구현 범위에 포함하지 않았습니다.

## 3. 수집과 Version 관리

### 3-1. 공고 이력 수집

초기에는 현재 DB에 존재하는 차수만으로 변경공고를 비교했지만, 실제 나라장터 원문 검수 과정에서 후속 차수가 누락된 사례를 발견했습니다.

이를 보완해 현재 수집 구조는 다음 방식으로 동작합니다.

```text
신규 공고 발견
→ 공고번호 기준 전체 이력 Backfill Queue 등록
→ 나라장터 전체 차수 조회
→ 차수 순 정렬
→ 최신 차수만 current version
```

기존 공고도 영속 Backfill Queue를 통해 점진적으로 다시 확인합니다.

대표 검증 사례인 `R26BK01634263`은 전체 이력 백필 후:

```text
000
001
002
003
004
005
```

총 6개 차수를 저장했고, `005` 취소공고를 최종 Current Version으로 확인했습니다.

### 3-2. 중복과 오류 격리

- `공고 ID + 나라장터 차수` 중복 방지
- 원본 내용 hash 기반 Version 관리
- 동일 URL / 파일 hash 기반 첨부 중복 방지
- 한 공고의 수집 오류가 전체 Polling을 중단하지 않도록 항목 단위 오류 격리
- Collection Run별 실패 수와 오류 요약 기록

즉 “수집 API 호출 성공”과 “업무적으로 최신 차수를 확보함”을 같은 의미로 사용하지 않습니다.

### 4-2. 파일 처리

- PDF: 페이지 단위 텍스트 추출
- HWP/HWPX: 구역·문단 단위 구조를 최대한 보존
- 추출 결과:
  - `extracted_text`
  - `extracted_blocks`
  - Source / Extracted SHA-256

추출 텍스트는 원본의 시각적 레이아웃을 완전히 보존하지 않으므로, 사용자에게 보여주는 최종 근거는 실제 첨부 원문과 함께 확인하도록 설계했습니다.

## 5. AI Core 전처리 파이프라인

| 단계 | 처리 | 목적 |
| --- | --- | --- |
| 1 | Document Parsing | 비정형 첨부를 검색 가능한 text/block으로 변환 |
| 2 | Semantic Chunking | 원문 구조를 활용한 의미 단위 분할 |
| 3 | Section / Keyword Candidate | 참가자격 후보 문맥 선택 |
| 4 | LLM Structured Extraction | 업종·지역·실적·인증 등 Requirement 구조화 |
| 5 | Grounding Validation | 모델 출력이 실제 원문에 존재하는지 대조 |
| 6 | Canonical Mapping | 자유 표현을 Canonical Type/Value로 정규화 |
| 7 | Requirement / Evidence 저장 | 판정과 원문 추적 가능 상태로 저장 |
| 8 | deterministic Judgment | 회사 Profile과 구조화 Requirement 비교 |

### AI Core Retrieval과 Copilot Retrieval은 다릅니다

AI Core의 Requirement Extraction 후보 선택은 현재:

```text
section-aware + keyword fallback
```

을 기본으로 사용합니다.

Copilot의 공개 공고문 질의는 별도 경로에서 준비된 index가 있을 때 Hybrid Retrieval을 우선 사용하며, broad/current-section/lexical fallback을 포함합니다.

따라서 프로젝트 전체를 하나의 “Vector RAG” 구조로 표현하지 않습니다.

## 6. 추출 안정성 개선

같은 공고를 반복 분석했을 때 Requirement 유형·값·근거 길이가 흔들리는 비결정성 문제를 실제 반복 실행으로 측정했습니다.

### 주요 개선

#### PR #133 — 지역 판정 안전성 + Golden Regression CI

- 상위 지역 정보만으로 하위 지역을 미달 확정하던 문제 수정
- 불확실한 경우 `UNSATISFIED` 대신 `UNKNOWN`
- Golden Set v0.2 고정 fixture 및 CI 추가
- Rule 회귀 기준 고정

#### PR #135 — Qualification Rule v0.3

- 지역 판정 의미 변경에 맞춰 Rule Version을 `qualification-rules-v0.3`으로 상향
- 오래된 v0.2 Judgment를 현재 화면·Copilot·affected-only 재검증에서 재사용하지 않도록 fail-closed
- Analysis / Notice Version / Company / Rule Version 호환성 확인

#### PR #136 — Extraction Determinism

- ANY_OF 대안 조건 구조화
- 이중 분류 병합
- 원문의 업종코드 salvage
- 회사 규모 표현 정규화
- 복합 조건의 잘못된 확정 경로 차단
- 저장 값과 Grounding Validation을 원문 기준으로 보강

대표 공고 반복 실행에서 Requirement 유형·값의 재현성이 크게 개선됐습니다.

다만 일부 공고에서는 raw 인용 길이, 코드가 없는 업종명, 제안요건/참가자격 경계처럼 추가 개선이 필요한 영역이 남아 있습니다. 이 한계는 Rule Golden Regression과 분리해서 관리합니다.

## 8. Golden Set과 Rule Regression

Golden Set은 팀 전체가 같은 공고와 회사 Profile로 개발·회귀·Demo를 반복하기 위한 고정 검증 데이터입니다.

| 항목 | 규모 |
| --- | ---: |
| 기준 공고 | 20 |
| 판정 Case | 40 |
| Canonical Requirement | 138 |
| 합성 회사 Profile | 32 |

현재 Golden Regression 기준:

```text
초안 기대값 일치      110 / 138
SAFE_ABSTENTION       28 / 138
잘못된 확정 판정      0
```

### 해석 주의

Golden Regression은 Canonical Requirement를 Rule Engine에 직접 넣습니다.

따라서 이 수치는:

- LLM Requirement Extraction 정확도
- RAG 답변 정확도
- 서비스 전체 정확도

가 아닙니다.

보증하는 범위는:

> **구조화 Requirement가 주어졌을 때 현재 Rule이 안전한 방향으로 회귀하지 않는가**

입니다.

실제 공고문 → Requirement Extraction 품질은 별도 반복실행·Grounding·Golden 평가로 봅니다.

## 9. 공용 DB 인프라

- PostgreSQL / Supabase 공용 DB
- Alembic으로 Schema Version 관리
- 공유 DB에 Migration lineage 유지
- 2026-09-16 Egress 이슈 대응으로 신규 Supabase 프로젝트로 데이터 이전
- 원본문서는 DB와 분리된 Document Storage 경로로 관리

DB Migration, 원본문서 저장소, 애플리케이션 데이터의 책임을 분리해 팀원이 동일한 Schema를 사용하도록 했습니다.

## 10. 최종 정리

데이터 파트에서 가장 중요하게 다룬 것은 “많이 수집했다”보다 다음 세 가지입니다.

1. **Version을 잃지 않는다.**
2. **추출 실패를 숨기지 않는다.**
3. **판정과 근거가 실제 원문까지 추적 가능해야 한다.**

변경공고 대응 서비스이기 때문에 최신 공고 한 건만 저장하는 것보다 **전체 이력과 판정 계보를 재현할 수 있는 데이터 구조**를 우선했습니다.
