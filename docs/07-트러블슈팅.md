# 07. Troubleshooting · 개선 과정

## 1. 자유 질문이 거의 동작하지 않음

### 문제

초기 Copilot은 추천 버튼이나 특정 키워드에서는 동작했지만, 사용자가 자연스럽게 질문하면 의도를 제대로 찾지 못했습니다.

E0 100문항 기준:

```text
Intent exact match
1 / 100
```

### 원인

deterministic keyword router가:

- `확인`
- `적용`
- `왜`
- `변경`

같은 substring을 너무 강하게 사용했습니다.

예를 들어 “중소기업 확인서가 적용되는지 설명해줘”에서:

- `확인` → Required Checks
- `적용` → Action Request

처럼 문장의 실제 의미보다 단어가 먼저 반응했습니다.

### 개선

1. 명확한 UI intent / write는 deterministic 유지
2. `UNKNOWN` 또는 weak read만 Semantic Router로 재검토
3. Semantic 분류가 실패하면 deterministic fallback

### 결과

```text
E0  1 / 100
E1 41 / 100
E2 100 / 100
```

### 배운 점

> 키워드를 계속 추가하는 것보다 **어떤 요청만 의미 분류로 넘길지 경계를 설계하는 것**이 중요했습니다.

## 2. Dense Retrieval만으로 필요한 근거를 잘 찾지 못함

### 문제

공공입찰 문서에는 자연어뿐 아니라:

- 업종코드
- 금액
- 기관명
- 자격증/확인서 명칭
- 법령 표현

같이 lexical match가 중요한 값이 많습니다.

Dense Retrieval:

```text
Recall@4 29.17%
```

### 개선

Dense와 BM25를 결합한 Hybrid Retrieval을 비교했습니다.

```text
Dense             29.17%
Hybrid            50.00%
Hybrid + Rerank   55.56%
```

### 기술 선택

Rerank가 가장 높은 수치를 보였지만 p50 latency가 약 2.85초까지 증가했습니다.

따라서 기본 경로는 Hybrid로 선택하고 Rerank는 기본 적용하지 않았습니다.

### 배운 점

> 가장 높은 offline metric이 항상 가장 좋은 Product 선택은 아닙니다.

## 3. Citation이 있어도 답변이 틀릴 수 있음

### 문제

초기 Grounded Answer에서는 Citation을 붙였다는 사실 자체가 안전성을 보장하지 못했습니다.

- 질문의 핵심과 관계없는 Source를 Citation
- 일부 조건만 근거가 있는데 전체 조건을 확정
- 원문 코드가 불완전하면 모델이 “정상적인 값”으로 고쳐서 답변

### 개선

Prompt를 v1 → v4로 개선했습니다.

```text
v1 Citation 존재
↓
v2 직접 근거 없으면 abstain
↓
v3 partial evidence를 전체 결론으로 확대 금지
↓
v4 원문 오류를 임의 복구하지 않음
```

이후 v3.1에서는 프롬프트뿐 아니라 구조적으로:

```text
Fact
Source
Claim
Validation
```

을 분리했습니다.

### 배운 점

> “근거를 붙여라”보다 **그 문장이 그 근거로 실제 뒷받침되는지 검증하는 구조**가 필요했습니다.

## 4. 자동테스트가 통과해도 실제 생성문이 저장 상태와 반대일 수 있음

### 문제

v3.1 감사 과정에서 다음 위험을 확인했습니다.

- 저장 판정은 ineligible인데 생성 산문이 반대 의미를 만들 가능성
- 수동 확인 항목의 citation 연결 누락
- 오래된 index/source를 현재 근거처럼 사용할 위험
- input 가능 여부 집계 오류

### 개선

```text
Server Fact
→ Source
→ Model Draft
→ Mechanical Validation
→ Semantic Validation
→ Repair 1회
→ Supported Claim만 게시
```

현재 Scope와 fingerprint를 응답 직전 다시 확인하도록 했습니다.

### 결과

지원되지 않는 Claim은 삭제하거나 PARTIAL로 반환합니다.

남원 Guided Job 실제 모델 평가 24턴 중 1건도 잘못된 Fact 참조의 추천 Claim이 제거되어 COMPLETE가 아니라 PARTIAL로 남았습니다.

### 배운 점

> 실패를 숨겨 완성된 답변처럼 보이게 하는 것보다 **안전하게 부분 성공을 반환하는 것이 더 중요**했습니다.

## 5. 높은 안전성을 얻었지만 응답이 느려짐

### 문제

v3.1은:

- Planning
- Product Read
- Generation
- Claim Validation
- 필요 시 Repair / Revalidation

을 수행하면서 복합 질문 latency가 커졌습니다.

Guided Job 실제 모델 평가:

```text
평균 약 26.92초
최대 약 54.13초
```

### 현재 판단

안전 검증을 제거해 속도를 얻기보다:

- Guided Job의 서버 고정 TaskPlan
- 불필요한 모델 호출 축소
- selective validation / retrieval
- hard query에서만 추가 처리

방향으로 개선해야 합니다.

### 배운 점

> AI 제품 품질은 정확도 하나가 아니라 **정확성 × 안전성 × latency × 비용**의 균형입니다.

## 6. 변경공고 차수 누락

### 문제

Golden 공고의 원문을 직접 대조하면서 팀 DB에 없는 후속 공고 차수를 발견했습니다.

즉:

```text
DB 최신 Version
≠ 나라장터 실제 최종 차수
```

인 상황이 발생할 수 있었습니다.

### 대응

- 나라장터 실제 관련공고 목록과 DB Version 직접 대조
- baseline/current 차수 검증
- 취소 공고 포함 여부 확인
- Golden Set에서 공고번호·차수·첨부문서 연결 검증 강화

### 배운 점

> 수집 파이프라인의 “성공”과 **업무적으로 최신 공고를 확보했다는 것**은 별도로 확인해야 합니다.

## 7. 문서가 코드보다 오래됨

### 문제

개발 속도가 빠르다 보니 상위 docs에는:

- Copilot Proposed
- Copilot API 미구현
- 예전 Rule Version
- 과거 Product Baseline

이 Current 상태처럼 남는 문제가 생겼습니다.

### 개선

문서 상태를 다음처럼 구분했습니다.

```text
Current
Proposed
Baseline Snapshot
Historical
Superseded
```

그리고 최종 단계에서는:

```text
Code / Test
→ 구현 저장소 Current docs
→ 제출용 docs
→ README 요약
```

순서로 정리했습니다.

### 배운 점

> AI로 개발 속도가 빨라질수록 코드만이 아니라 **설명 가능한 현재 상태를 유지하는 문서 관리**가 더 중요해집니다.
